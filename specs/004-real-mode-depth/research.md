# Research: Real Mode Depth -- Comparison & Cost Tracking

**Feature**: `004-real-mode-depth` | **Date**: 2026-08-10

`/speckit.clarify` (2026-08-10) already resolved five ambiguities
directly in spec.md (view placement, comparison scope, default
threshold, ledger persistence, no-key behavior -- see spec.md's
Clarifications section). This file resolves the remaining decisions
needed before Phase 1 design, each grounded in the actual shipped code
(`src/concepts/rag/`), not assumed from the spec alone.

## Decision: Simulated half for HyDE/RAG-Fusion configurations

**Decision**: Regardless of which configuration (`naive`, `hyde`,
`fusion`) the learner selects in the comparison view, the Simulated half
**always computes and shows naive RAG's simulated ranking** (the same
`chunkText` -> `embed` -> `cosineSimilarity` pipeline
`RetrievalStep.tsx` already runs). When the selected configuration isn't
`naive`, the Simulated panel additionally renders an explicit caveat --
"Simulated Mode approximates HyDE/RAG-Fusion as plain retrieval here,
since it has no model to generate hypotheses or reworded queries" --
using the same disclosure-marker convention (`data-simulated-
disclosure="true"`-style) `check:disclosure` already enforces elsewhere.

**Rationale**: HyDE's hypothesis text and RAG-Fusion's reworded queries
are both generated by a real model call in this codebase
(`buildHypothesisPrompt`/`buildQueryVariantPrompt` in
`variantExecution.ts`, consumed only by `provider.generate()`).
`mockEmbedding.ts` is a deterministic bag-of-words *embedding*
projection -- it has no text-generation capability at all, and
`GenerationStep.tsx`'s mock generator is a template summary of an
*already-retrieved* top chunk, which is circular for HyDE (which needs a
hypothesis *before* retrieval happens). There is no existing "simulated
HyDE" or "simulated RAG-Fusion" anywhere in the shipped code today --
`VariantsComparison.tsx`'s non-real state only ever shows descriptive
flow diagrams for these two, never a computed ranking. Fabricating a
synthetic hypothesis (e.g., reusing the query text verbatim, or running
it through the mock generator anyway) would produce a *convincing-
looking* but not-actually-representative "simulated HyDE" -- exactly
the Constitution Principle II failure mode ("a convincing-looking fake
that isn't labeled teaches the wrong lesson as confidently as a real
one"). Showing the real, already-honest naive-RAG simulated ranking
with an explicit "this is an approximation" caveat is strictly more
honest, and still serves User Story 1's actual teaching goal: the
learner sees exactly how Real Mode's HyDE/RAG-Fusion ranking diverges
from the deterministic simulated baseline they already understand from
Pipeline Walkthrough.

**Alternatives considered**: Synthesizing a deterministic pseudo-
hypothesis (e.g., "hypothesis := query, embedded and treated as if it
were a real hypothesis") was rejected -- it would produce a ranking that
*looks* like a legitimate "Simulated HyDE" result but doesn't reflect
what HyDE's actual mechanism (a generated, elaborated guess at the
answer) does, misleading exactly the learners this principle exists to
protect. Disabling HyDE/RAG-Fusion selection entirely when Real Mode
isn't active was also considered but rejected: FR-002a and the
`/speckit.clarify` answer both establish the selector as always
available (its Real half is what's gated on Real Mode/API key per
FR-004a, not the selector itself).

## Decision: Cost ledger as a `RealModeProvider` decorator

**Decision**: `createLedgerTrackingProvider(base: RealModeProvider,
pricing: PricingTable, onCallRecorded: (entry: CostLedgerEntry) =>
void): RealModeProvider` wraps `embedBatch`/`generate` with the *same*
signatures, appending exactly one `CostLedgerEntry` immediately after
each underlying call **resolves successfully** (never on rejection) and
otherwise passing the call straight through. Every existing real-call
site swaps `createOpenAICompatibleProvider(realMode.provider,
realMode.apiKey)` for a new one-line helper,
`createTrackedProvider(realMode, onCall)`, that composes the decorator
around the existing adapter -- no other line in any of the five call
sites (`RetrievalStep.tsx`, `EmbeddingStep.tsx`, `GenerationStep.tsx`,
`VariantsComparison.tsx`, `EvalPanel.tsx`) changes, since the decorator
satisfies the exact same `RealModeProvider` interface its caller already
depends on.

**Rationale**: Directly resolves spec.md's Edge Case ("a failed call
that made no billable request should not be added to the total; a
failed call that did consume quota before failing should be") --
per-call, post-resolution accounting is the only way to get this right
without guessing at provider-specific partial-failure billing
semantics. It's also the smallest possible blast radius: every call
site in this codebase already constructs its own `RealModeProvider`
instance at the point of use, so wrapping that one construction call is
a one-line change per site, consistent with tech-stack.md's existing
"one function, one seam" swap-out philosophy (the same pattern
`mockGenerate()`'s isolation and the `RealModeProvider`
interface itself already establish).

**Alternatives considered**: A global fetch-interception layer
(instrumenting `openaiCompatibleProvider.ts`'s `fetch` calls directly)
was rejected -- it would blur the provider adapter's responsibility
(speaking the OpenAI-compatible REST shape) with an unrelated one
(cost bookkeeping), and would make `openaiCompatibleProvider.ts`
untestable in isolation from the ledger. A per-caller manual
`onCallRecorded()` invocation at every `await provider.embedBatch(...)`
/`await provider.generate(...)` call site was also considered but
rejected: it requires touching every call *inside* five files' control
flow (including error branches) rather than one line per file, and
risks a caller forgetting to record a call the decorator can never
miss.

## Decision: Flat per-call pricing, not per-token metering

**Decision**: `PricingTable` holds two flat, static USD figures --
`embedCallUsd` and `generateCallUsd` -- rather than per-token rates
requiring actual token counts. `openaiPricing` derives these once from
published per-token rates and a documented *assumed* typical call size
(disclosed in the pricing-assumption label, FR-008):

```
embedCallUsd    = (500 assumed tokens / 1,000,000) * $20/1M tokens  = $0.00001
generateCallUsd = (400 assumed input tokens / 1,000,000) * $150/1M
                + (150 assumed output tokens / 1,000,000) * $600/1M = $0.00015
```

**Rationale**: `openaiCompatibleProvider.ts`'s `fetch`-based adapter
doesn't parse or expose the response's `usage` token counts today (see
`realMode/openaiCompatibleProvider.ts` -- it returns only the embedding
vectors / generated text), and spec.md's own Assumptions explicitly rule
out a live pricing lookup or added complexity here ("a single
configurable pricing table per provider, maintained as static
configuration"). This also mirrors the *existing* app's own precedent:
`callEstimate.ts`'s `naiveCallCount()`/`hydeCallCount()`/
`fusionCallCount()` already estimate cost in flat call counts, not token
counts, for the exact same reason. Building genuine per-token metering
would require plumbing `usage` fields through every adapter response and
every caller -- a materially larger change than this milestone's scope,
for precision spec.md doesn't ask for ("never presented as an exact
bill" explicitly allows an approximation).

**Alternatives considered**: Parsing real `usage.total_tokens` from each
OpenAI response was considered -- more accurate, but rejected as
out-of-scope: it would require `openaiCompatibleProvider.ts` to change
its return shape (today just `number[][]`/`string`) to also carry usage
metadata, rippling through every caller's type signature for a milestone
whose spec explicitly scopes cost to "estimate," not exact.

## Decision: Where the comparison view's document/question state lives

**Decision**: `CompareSimulatedVsReal.tsx` owns its own independent
`docId`/`customMode`/`query` state, exactly like `VariantsComparison.tsx`
already does -- not shared with `PipelineWalkthrough.tsx`.

**Rationale**: This mirrors Milestone 2's own established "independent
state" precedent for Compare Variants (each top-level view keeps its own
document/query state rather than sharing `RagConcept.tsx`-lifted state)
-- consistent with the new view being a third sibling tab (this
plan's/spec's clarified placement decision), not a mode of Pipeline
Walkthrough. `realMode`, `generationParams`, `topK`, and the new
`costLedger` are lifted to `RagConcept.tsx` and threaded as props to all
three views, matching the existing pattern exactly.

## Decision: Warning-threshold gate mechanism (FR-007)

**Decision**: Every real-call-triggering action (`RetrievalStep`'s
corpus/query embed effects and sweep confirm, `EmbeddingStep`,
`GenerationStep`, `VariantsComparison`'s Run buttons, `EvalPanel`'s Run,
the new comparison view's Run) checks `sumLedger(costLedger) >=
costLedger.warningThresholdUsd` immediately before firing its next real
call. If crossed, the action shows `CostWarningBanner` inline (same
placement convention as `ErrorBanner`) with a "Proceed anyway" button
that must be explicitly clicked before the underlying call fires --
mirroring `RetrievalStep.tsx`'s existing `awaiting-confirmation` /
"Start sweep" two-step shape (research.md precedent from 003-parameter-
exploration) rather than inventing a new confirmation idiom.

**Rationale**: FR-007 requires the warning to appear "before the next
real call is made, not only after the fact" -- a pre-call gate, not a
post-hoc banner. Reusing the sweep's already-accessibility-verified
two-step confirm pattern (`tests/a11y/parameter-exploration.spec.ts`
already covers keyboard operability for this shape) is lower-risk than
a new pattern, and keeps every call site's change small: one guard
condition plus one shared, reusable banner component.

## Decision: Reset-prompt mechanism for a document/pipeline-state change (FR-006)

**Decision**: `SessionCostLedger` gains a `pendingResetPrompt: boolean`
field. Any doc-change or reset handler that already exists in the
codebase (`PipelineWalkthrough.tsx`'s `handleDocSelect`,
`VariantsComparison.tsx`'s `handleDocSelect`/`handleUseCustomDocument`/
`handleRevertToSample`, the new comparison view's own doc-change
handler, and `FailurePresetPicker`'s "Reset to defaults") additionally
sets `pendingResetPrompt: true` on the lifted ledger state (via a new
`onLedgerResetPrompt` callback threaded down alongside `costLedger`).
`CostLedgerDisplay.tsx` (always visible, per FR-005) renders a small
confirm banner whenever `pendingResetPrompt` is true, with two buttons --
"Keep accumulating" and "Reset total" -- both of which clear the flag;
the total itself only changes if "Reset total" is chosen.

**Rationale**: Directly answers FR-006's requirement to *ask*, not
silently do either. Because the ledger already lives in one place
(`RagConcept.tsx`, lifted) while the state that triggers this prompt is
scattered across three views' own doc-change handlers, a shared boolean
flag plus one shared display component is the smallest change that
still surfaces the prompt from wherever it was triggered -- consistent
with `CostLedgerDisplay`'s own FR-005 requirement to be visible from any
step/view already.

## Decision: `check:disclosure` and `check:extensibility`/`check:determinism` scope

**Decision**: `check:extensibility` and `check:determinism` need no new
rule -- this feature's Simulated-side computation is the same already-
deterministic pipeline, and every new file lives inside
`src/concepts/rag/`. `check:disclosure` gains one new rule: when
`CompareSimulatedVsReal` is rendered with a non-`naive` configuration
selected, its Simulated panel must carry a `data-simulated-disclosure`-
style element whose text names the approximation explicitly (research.md's
"Simulated half for HyDE/RAG-Fusion" decision), mirroring the existing
`checkSurface`/`checkRealDisclosure` helper functions already in
`scripts/checks/simulated-disclosure.ts`.

**Rationale**: Consistent with how this script has grown a new rule per
milestone (FR-004's `data-real-disclosure` rule for 002-real-mode,
unchanged since) rather than becoming a new script -- this feature's one
new disclosure surface fits the same pattern exactly.
